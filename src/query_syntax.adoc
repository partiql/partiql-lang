[[sec:query-syntax]]
== PartiQL Query Syntax

PartiQL extends SQL's query capabilities to work seamlessly with nested and semi-structured data while maintaining full backward compatibility with SQL. This section describes the syntax and semantics of PartiQL queries, with particular attention to how data flows through query clauses via binding tuples.

[[sec:query-structure]]
=== Query Structure

PartiQL queries follow the SFW (Select-From-Where) model familiar from SQL, extended with additional clauses for handling complex data structures. A complete PartiQL query may include the following clauses:

[source, partiql]
----
SELECT <select_list> | SELECT VALUE <expression> | PIVOT <expression> AT <expression>
FROM <data_source>
[ LET <variable_bindings> ]
[ WHERE <condition> ]
[ GROUP BY <grouping_expressions> [ GROUP AS <group_variable> ] ]
[ HAVING <condition> ]
[ ORDER BY <ordering_expressions> ]
[ LIMIT <number> ]
[ OFFSET <number> ]
----

Not all clauses are required. The minimal query consists of a `SELECT` (or `SELECT VALUE` or `PIVOT`) and `FROM` clause.

[[sec:clause-exec-order]]
=== Clause Execution Order

PartiQL clauses are evaluated in the following logical order, which differs from their textual order in the query:

1. **FROM** - Establishes data sources and creates initial binding tuples
2. **LET** - Adds computed variables to binding tuples
3. **WHERE** - Filters binding tuples based on conditions
4. **GROUP BY** - Partitions binding tuples into groups
5. **HAVING** - Filters groups based on aggregate conditions
6. **SELECT / SELECT VALUE / PIVOT** - Transforms binding tuples into output values
7. **ORDER BY** - Orders the output (converting bags to arrays)
8. **LIMIT / OFFSET** - Restricts the number of output values

Understanding this execution order is crucial for comprehending variable scoping and when each expression can reference which variables.

[[sec:binding-tuple-flow]]
=== Binding Tuples and Data Flow

PartiQL's compositional semantics are based on the flow of _binding tuples_ through query clauses. Each clause:

1. Receives a collection (bag or array) of binding tuples as input
2. Evaluates expressions within the context of each binding tuple
3. Produces a collection of binding tuples as output for the next clause

A binding tuple has the form `<<x₁:v₁, ..., xₙ:vₙ>>` where each `xᵢ` is a variable name bound to a value `vᵢ`. For example, `<<customer: {'id':1, 'name':'Alice'}, order: {'id':100}>>` binds variable `customer` to a tuple and variable `order` to another tuple.

When a clause evaluates an expression, it does so within an environment formed by:

* The _database environment_ containing database object bindings
* The _variables environment_ formed by concatenating the query's variable bindings with the current binding tuple

This uniform treatment of binding tuples allows each clause to be understood independently while maintaining a clear flow of data through the query pipeline.

[[sec:from-clause]]
=== FROM Clause

The `FROM` clause establishes the data sources for a query and creates the initial set of binding tuples that flow through subsequent clauses.

==== Basic Syntax

[source, partiql]
----
FROM <expression> [ AS ] <variable> [ AT <position_variable> ]
----

The `FROM` clause evaluates an expression that typically refers to a database collection (table, array, bag) and binds each element to a variable. The optional `AT` clause binds the position (index) of each element.

==== Ranging Over Collections

When the `FROM` clause ranges over a collection, it produces one binding tuple for each element in the collection.

For an array `[e₀, e₁, ..., eₙ₋₁]`, the clause:
[source, partiql]
----
FROM array_expression AS v AT p
----

produces binding tuples `<<v:e₀, p:0>>`, `<<v:e₁, p:1>>`, ..., `<<v:eₙ₋₁, p:n-1>>`.

For a bag, the `AT` clause produces `MISSING` for the position variable since bags are unordered.

==== Input and Output Binding Tuples

*Input:* The `FROM` clause starts with an empty variables environment (or the environment from an enclosing query for subqueries).

*Processing:* For each element in the data source, the `FROM` clause creates a binding tuple that binds the element variable (and optionally the position variable) to the corresponding values.

*Output:* A bag of binding tuples, denoted B_FROM^out, where each tuple contains bindings for the variables defined by the `FROM` clause.

If the data source is an array and no subsequent `ORDER BY` clause disrupts the order, the output maintains the array's ordering. Otherwise, the output is an unordered bag.

==== Type Coercion and Error Handling

In permissive mode, if the `FROM` expression evaluates to:

* A scalar value: It is coerced to a single-element bag
* A tuple: It is coerced to a single-element bag
* `NULL` or `MISSING`: It is coerced to a single-element bag containing the absent value

In type checking mode, these cases result in type errors.

==== UNPIVOT

The `UNPIVOT` operation transforms a tuple into a collection of attribute-value pairs, enabling iteration over a tuple's contents.

[source, partiql]
----
FROM UNPIVOT <tuple_expression> AS <value_variable> AT <name_variable>
----

For a tuple `{'a₁':v₁, ..., 'aₙ':vₙ}`, `UNPIVOT` produces binding tuples:

* `<<value_variable:v₁, name_variable:'a₁'>>`
* `<<value_variable:v₂, name_variable:'a₂'>>`
* ...
* `<<value_variable:vₙ, name_variable:'aₙ'>>`

This is particularly useful for schema-agnostic queries that need to process tuple attributes dynamically.

*Binding Tuples Flow:* `UNPIVOT` takes a tuple and generates one binding tuple for each attribute-value pair, with the attribute name bound to one variable and the attribute value bound to another.

[[sec:joins]]
=== JOINs

PartiQL supports various join operations that combine binding tuples from multiple data sources.

==== CROSS JOIN

The syntax:
[source, partiql]
----
<left> CROSS JOIN <right>
<left>, <right>
<left> JOIN <right> ON TRUE
----

are all equivalent and produce the Cartesian product of binding tuples from the left and right sides.

*Binding Tuples Flow:*

* Input: Binding tuples from evaluating the left expression (B_left)
* Processing: For each binding tuple b_left in B_left, evaluate the right expression in the environment extended with b_left. This produces binding tuples B_right.
* Output: For each combination of b_left and b_right, produce the concatenated binding tuple (b_left || b_right)

Importantly, the right side can reference variables defined by the left side, enabling correlated joins and nested data access patterns.

==== LEFT JOIN

The syntax:
[source, partiql]
----
<left> LEFT JOIN <right> ON <condition>
<left> LEFT CROSS JOIN <right>
----

performs a left outer join, preserving all binding tuples from the left side even when no matching right-side binding tuples exist.

*Binding Tuples Flow:*

* Input: Binding tuples B_left from the left expression
* Processing: For each b_left, evaluate the right expression to get B_right. Filter B_right based on the ON condition.
* Output: 
** If B_right is empty or no tuples satisfy the condition: Produce (b_left || <<v₁:NULL, ..., vₙ:NULL>>) where v₁...vₙ are variables defined by the right side
** Otherwise: Produce (b_left || b_right) for each qualifying b_right

==== FULL JOIN

[source, partiql]
----
<left> FULL JOIN <right> ON <condition>
----

The `FULL JOIN` provides SQL's full outer join semantics. Unlike `CROSS JOIN` and `LEFT JOIN`, the right side of a `FULL JOIN` cannot reference variables from the left side (consistent with SQL).

==== JOIN with ON Condition

The `ON` clause specifies a join condition:

[source, partiql]
----
<left> JOIN <right> ON <condition>
----

This is equivalent to:
[source, partiql]
----
<left> CROSS JOIN <right>
WHERE <condition>
----

However, the `ON` form is often more readable and makes the join relationship explicit.

*Binding Tuples Flow:* The `ON` condition is evaluated in the environment formed by concatenating left and right binding tuples. Only tuples where the condition evaluates to `true` are included in the output.

==== LATERAL

The `LATERAL` keyword can be used for SQL compatibility:
[source, partiql]
----
<left>, LATERAL <right>
----

This is equivalent to `<left>, <right>`. PartiQL allows correlation by default, so `LATERAL` is optional but may be included for clarity or SQL compatibility.

[[sec:where-clause]]
=== WHERE Clause

The `WHERE` clause filters binding tuples based on a boolean condition, passing through only those tuples for which the condition evaluates to `true`.

==== Syntax

[source, partiql]
----
WHERE <condition>
----

==== Semantics

The `WHERE` clause evaluates its condition for each input binding tuple. The condition is evaluated within the environment formed by the database environment and the variables defined in the binding tuple.

*Binding Tuples Flow:*

* Input: B_WHERE^in (the bag of binding tuples from preceding clauses)
* Processing: For each binding tuple b in B_WHERE^in, evaluate the condition in the environment (p₀, p || b)
* Output: B_WHERE^out contains only those binding tuples where the condition evaluated to `true`

==== Three-Valued Logic

PartiQL follows SQL's three-valued logic, where conditions can evaluate to `true`, `false`, or `NULL`/`MISSING`. Only binding tuples where the condition is `true` pass through the `WHERE` clause.

If the condition evaluates to:

* `true`: The binding tuple is included in the output
* `false`: The binding tuple is excluded
* `NULL` or `MISSING`: The binding tuple is excluded
* A non-boolean value: The binding tuple is excluded (in permissive mode)

==== NULL and MISSING

PartiQL has two types of absent values: `NULL` and `MISSING`. In boolean expressions, they behave identically:

* `NULL AND TRUE` → `NULL`
* `MISSING AND TRUE` → `NULL`
* `NULL OR FALSE` → `NULL`
* `MISSING OR FALSE` → `NULL`

The predicate `IS MISSING` can distinguish between them:

* `NULL IS MISSING` → `false`
* `MISSING IS MISSING` → `true`

==== Type Errors in Permissive Mode

In permissive mode, type errors in the `WHERE` condition are treated as `false`. For example, comparing a string to a number fails gracefully by filtering out the binding tuple rather than aborting the query.

[[sec:group-by-clause]]
=== GROUP BY Clause

The `GROUP BY` clause partitions binding tuples into groups based on the values of grouping expressions, enabling aggregation and group-level computations.

==== Core Syntax

[source, partiql]
----
GROUP BY <expression> AS <variable> [, ...] GROUP AS <group_variable>
----

The `GROUP BY` clause defines:

* _Grouping expressions_: Expressions whose values determine group membership
* _Grouping variables_: Variables that hold the computed grouping expression values
* _Group variable_: A variable that holds all binding tuples in the group

==== Semantics

The input binding tuples are partitioned into groups where all tuples in a group have equivalent values for all grouping expressions. The equivalence function used for grouping treats `NULL` and `MISSING` as equal (both are coerced to `NULL` before comparison) and considers two non-null values equivalent if they compare equal according to the equality operator.

*Binding Tuples Flow:*

* Input: B_GROUP^in (bag of binding tuples from preceding clauses)
* Processing: Partition B_GROUP^in into equivalence groups based on grouping expression values
* Output: B_GROUP^out where each binding tuple represents one group and has the form:
  `<<x₁:v₁, ..., xₘ:vₘ, g:B_j>>`
  where x₁...xₘ are grouping variables with their group's shared values, and g is the group variable containing all binding tuples in that group

==== The Group Variable

The group variable explicitly contains all binding tuples that belong to the group. This makes PartiQL's grouping more powerful than SQL's, as the full group data is available for complex computations beyond standard aggregate functions.

The binding tuples within the group variable retain all variables from the `FROM` and `LET` clauses. This allows sophisticated operations on the grouped data.

==== GROUP ALL

The `GROUP ALL` variant creates a single group containing all input binding tuples, regardless of whether any tuples exist:

[source, partiql]
----
GROUP ALL AS <group_variable>
----

This is useful for SQL compatibility when computing aggregates over an entire result set without explicit grouping criteria.

*Binding Tuples Flow:* `GROUP ALL` always produces exactly one output binding tuple containing the group variable. If the input is empty, the group variable is an empty bag.

==== SQL Compatibility Features

For SQL compatibility, PartiQL supports several syntactic conveniences:

===== Implicit Group Variable

When using SQL aggregate functions (like `COUNT`, `SUM`, `AVG`) without an explicit group variable, PartiQL automatically supplies the group variable. If a `GROUP BY` exists, it's augmented with `GROUP AS g` where `g` is a fresh variable. If no `GROUP BY` exists, `GROUP ALL AS g` is added.

The aggregate function call is rewritten to operate on the group variable. For example, `AVG(x.price)` becomes `AVG(SELECT VALUE p.x.price FROM g AS p)`.

===== Grouping Without Variable Names

SQL allows grouping expressions without binding them to variables:
[source, partiql]
----
GROUP BY <expression>
----

This is syntactic sugar for:
[source, partiql]
----
GROUP BY <expression> AS x
----

where `x` is a system-generated variable name.

===== Using SELECT Aliases in GROUP BY

For SQL compatibility, aliases defined in the `SELECT` clause can be used in the `GROUP BY` clause:
[source, partiql]
----
SELECT expr AS alias
FROM ...
GROUP BY alias
----

This is rewritten to:
[source, partiql]
----
SELECT expr AS alias
FROM ...
GROUP BY expr
----

[[sec:having-clause]]
==== HAVING Clause

The `HAVING` clause filters groups after grouping has occurred:

[source, partiql]
----
HAVING <condition>
----

*Binding Tuples Flow:*

* Input: B_HAVING^in (binding tuples output from `GROUP BY`, where each tuple represents a group)
* Processing: Evaluate the condition for each binding tuple in the extended environment
* Output: B_HAVING^out contains only those binding tuples where the condition evaluated to `true`

The `HAVING` clause behaves like a `WHERE` clause but operates on group-level binding tuples. It can reference grouping variables and the group variable, and typically includes aggregate functions.

[[sec:select-value-clause]]
=== SELECT VALUE Clause

The `SELECT VALUE` clause is PartiQL's core output mechanism, producing a collection of values (not necessarily tuples) from binding tuples.

==== Syntax

[source, partiql]
----
SELECT VALUE <expression>
----

==== Semantics

The `SELECT VALUE` clause evaluates its expression for each input binding tuple and collects the results into a bag (or array, if `ORDER BY` is present).

*Binding Tuples Flow:*

* Input: B_SELECT^in (binding tuples from preceding clauses)
* Processing: For each binding tuple b in B_SELECT^in, evaluate the expression in environment (p₀, p || b) to produce a value v
* Output: A bag or array of values (not binding tuples): <<v₁, v₂, ..., vₙ>>

Unlike SQL's `SELECT`, which always produces a collection of tuples, `SELECT VALUE` can produce a collection of any values: scalars, arrays, bags, tuples, or heterogeneous collections.

==== Constructors in SELECT VALUE

The `SELECT VALUE` expression frequently uses constructors to build structured output:

===== Tuple Constructors

[source, partiql]
----
SELECT VALUE {'attr1': expr1, 'attr2': expr2}
----

Constructs tuples with specified attributes. Attribute names are expressions (typically string literals) and values are arbitrary expressions.

===== Array Constructors

[source, partiql]
----
SELECT VALUE [expr1, expr2, expr3]
----

Constructs fixed-length arrays.

===== Bag Constructors

[source, partiql]
----
SELECT VALUE <<expr1, expr2, expr3>>
----

Constructs bags (unordered collections with duplicates).

==== Treatment of MISSING

The handling of `MISSING` values differs based on the constructor:

* *In tuple constructors*: If an attribute value evaluates to `MISSING`, the attribute is omitted from the tuple
* *In array constructors*: `MISSING` values are included in the array
* *In bag constructors*: `MISSING` values are included in the bag
* *As direct output*: `MISSING` values are included in the result collection

==== Type Errors in Tuple Constructors

When constructing tuples, if an attribute name expression evaluates to a non-string value:

* In permissive mode: The attribute is omitted
* In type checking mode: An error is raised

If a tuple constructor produces duplicate attribute names, both attributes are included in the tuple (PartiQL tuples can have duplicate attribute names).

[[sec:select-clause]]
=== SELECT Clause

The SQL `SELECT` clause is syntactic sugar over `SELECT VALUE` that specifically constructs tuples. It provides SQL compatibility while leveraging PartiQL's underlying `SELECT VALUE` semantics.

==== Syntax

[source, partiql]
----
SELECT <expr1> AS <name1>, <expr2> AS <name2>, ...
----

==== Desugaring to SELECT VALUE

The SQL `SELECT` clause:
[source, partiql]
----
SELECT e1 AS a1, e2 AS a2, ..., en AS an
----

is equivalent to:
[source, partiql]
----
SELECT VALUE {'a1': e1, 'a2': e2, ..., 'an': an}
----

==== Implicit Attribute Names

When an alias is omitted, PartiQL infers an attribute name:

* If the expression is a path ending in an attribute name (e.g., `x.attr`), the attribute name is used
* Otherwise, a system-generated name is used (implementation-dependent)

For example:
[source, partiql]
----
SELECT x.price, x.quantity * 2
----

is equivalent to:
[source, partiql]
----
SELECT x.price AS price, x.quantity * 2 AS _2
----

(where `_2` represents a system-generated name)

==== SELECT *

The `SELECT *` syntax expands to include all attributes from tuple-valued variables:

[source, partiql]
----
SELECT x.*
----

When `x` is bound to a tuple, this includes all attributes of `x` in the output tuple. When `x` is not a tuple, it is coerced to a singleton tuple with a system-generated attribute name.

Multiple `*` items and regular expressions can be combined:
[source, partiql]
----
SELECT x.*, expr AS name, y.*
----

This uses the `TUPLEUNION` function to combine attributes from multiple sources into a single tuple. Duplicate attribute names may result.

*Binding Tuples Flow:*

* Input: B_SELECT^in (binding tuples from preceding clauses)
* Processing: For each binding tuple b, evaluate the SELECT expressions and construct a tuple
* Output: A bag or array of tuples (one tuple per input binding tuple)

[[sec:pivot-clause]]
=== PIVOT Clause

The `PIVOT` clause constructs a single tuple with a data-dependent number of attributes, where both attribute names and values come from the data.

==== Syntax

[source, partiql]
----
PIVOT <value_expression> AT <name_expression>
----

==== Semantics

Unlike `SELECT VALUE` which produces a collection, `PIVOT` produces a single tuple. For each input binding tuple, it evaluates the name expression (which should yield a string) and the value expression, creating an attribute-value pair in the output tuple.

*Binding Tuples Flow:*

* Input: B_PIVOT^in (bag or array of binding tuples)
* Processing: For each binding tuple b in B_PIVOT^in, evaluate both expressions in environment (p₀, p || b) to produce an attribute name a and value v
* Output: A single tuple containing all attribute-value pairs: {'a₁':v₁, 'a₂':v₂, ..., 'aₙ':vₙ}

The output is always an unordered tuple, even if the input was an ordered array.

==== Treatment of MISSING and Type Errors

If a name expression evaluates to:

* `MISSING`: The attribute is omitted from the output tuple
* A non-string: In permissive mode, the attribute is omitted; in type checking mode, an error is raised

If a value expression evaluates to `MISSING`, the attribute is omitted.

[[sec:order-by-clause]]
=== ORDER BY Clause

The `ORDER BY` clause sorts the query output, converting a bag into an array.

==== Syntax

[source, partiql]
----
ORDER BY <expr1> [ASC|DESC] [NULLS FIRST|NULLS LAST],
         <expr2> [ASC|DESC] [NULLS FIRST|NULLS LAST],
         ...
----

or:

[source, partiql]
----
ORDER BY PRESERVE
----

==== Semantics

The `ORDER BY` clause evaluates its ordering expressions for each input binding tuple (when ordering after `GROUP BY` or at the top level) or for each output value (when ordering after `SELECT VALUE`).

*Binding Tuples Flow:*

* Input: B_ORDER^in or a bag/array of values (depending on clause position)
* Processing: Evaluate ordering expressions and sort using the order-by less-than function
* Output: An array with elements in sorted order

==== Order-By Less-Than Function

PartiQL's order-by less-than function extends SQL's ordering to handle heterogeneous types:

1. `NULL` and `MISSING` compare equal and are first (with `NULLS FIRST`) or last (with `NULLS LAST`)
2. Boolean values: `false` < `true`
3. Numbers: ordered numerically (special values: `nan` < `-inf` < numbers < `+inf`)
4. Timestamps: ordered by absolute point in time
5. Text strings: ordered lexicographically by Unicode scalar
6. Binary LOBs: ordered lexicographically by octet
7. Arrays: ordered lexicographically by element comparison
8. Tuples: ordered lexicographically by sorted attributes (name first, then value)
9. Bags: converted to sorted arrays, then compared

==== ASC and DESC

* `ASC` (ascending, the default): orders from smallest to largest
* `DESC` (descending): orders from largest to smallest

==== NULLS FIRST and NULLS LAST

* `NULLS FIRST`: places `NULL` and `MISSING` values at the beginning
* `NULLS LAST`: places `NULL` and `MISSING` values at the end

The default is `NULLS FIRST` for `ASC` and `NULLS LAST` for `DESC` (matching SQL).

==== PRESERVE

The `ORDER BY PRESERVE` directive preserves the input order when the input is an array. This is useful when you want to maintain the original array ordering through query evaluation.

==== SQL Compatibility

For SQL compatibility, ordering expressions can reference attributes of tuple-valued results directly, without explicitly referencing a variable. Additionally, aliases defined in the `SELECT` clause can be used in `ORDER BY` expressions.
