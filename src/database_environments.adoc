[[sec:environments-and-variables]]
== Environments and Variables

PartiQL queries are evaluated within environments that provide the context for name resolution and variable binding. This section explains how PartiQL manages database objects and variables through a two-tier environment system.

[[sec:binding-tuples]]
=== Binding Tuples

A _binding tuple_ is the fundamental data structure used to represent environments in PartiQL. A binding tuple is a collection of name-value pairs: stem:[<<x_1:v_1,...,x_n:v_n>>], where each stem:[x_i] is a unique name that binds to a value stem:[v_i].

*Key Properties:*

* Similar to PartiQL tuples, but used internally for semantic operations
* All names within a binding tuple are unique
* Explicitly represents variables with `MISSING` values rather than omitting them
  ** Example: stem:[<<x : 1, y: "MISSING">>] instead of stem:[<<x : 1>>]
  ** This distinction is important: the absence of a variable name differs from a variable whose value is `MISSING`

*Binding Tuple Concatenation:*

Two binding tuples stem:[b] and stem:[b'] can be concatenated as stem:[b||b']:

* The result contains all bindings from both tuples
* If the same name appears in both, stem:[b']'s binding takes precedence (right argument wins)
* This operation implements variable shadowing in nested scopes

.EBNF Grammar for Names
[source, ebnf]
----
bind_name = global_name | variable ;
qualified_name = identifier, ".", identifier, { ".", identifier } ;
variable_name = identifier ;
identifier = ("$"|"_"|letter), { ("$"|"_"|letter|digit) }
           | '"', ? quoted identifier body ?, '"' ;
----

[[sec:database-environment]]
=== Database Environment

The *database environment* (stem:[p_0]) is analogous to global scope in traditional programming languages. It contains persistent, named database objects that are visible throughout query execution.

==== Contents

The database environment includes:

* *Tables* - relational data collections
* *Views* - virtual tables defined by queries
* *Qualified names* - hierarchical names like `catalog.schema.table`
* *System objects* - built-in functions and metadata tables

==== Qualified Names

Qualified names enable hierarchical organization of database objects:

[source, ebnf]
----
qualified_name = identifier, ".", identifier, { ".", identifier } ;
----

*Examples:*

* `mydb.users` - database `mydb`, table `users`
* `catalog.schema.table` - three-part qualified name
* `system.information_schema.columns` - system catalog access

IMPORTANT: A qualified name like `mydb.users` is distinct from a quoted identifier `"mydb.users"`. The former is two separate identifiers forming a path; the latter is a single identifier containing a dot character.

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
SELECT x.id, x.name
FROM company.hr.employees AS x
WHERE x.department = 'Engineering'
----

The qualified name `company.hr.employees` exists in the database environment stem:[p_0].
====

==== Modifying the Database Environment

Only certain DDL (Data Definition Language) commands modify the database environment:

* `CREATE TABLE` - adds a new table
* `CREATE VIEW` - adds a new view
* `DROP TABLE` / `DROP VIEW` - removes objects
* `ALTER TABLE` - modifies table structure

Query execution (SELECT, INSERT, UPDATE, DELETE) does not modify the database environment—it only reads from stem:[p_0] and modifies data values.

==== Characteristics

* *Global scope* - visible throughout all queries
* *Persistent* - exists beyond individual query executions
* *Immutable during queries* - stays constant while a query runs
* *Established externally* - populated by DDL commands, not by SELECT queries

[[sec:lexical-scoping]]
=== Lexical Scoping

PartiQL uses *lexical scoping* for variables, where the scope of a variable is determined by its position in the query text. Variables are introduced by specific clauses and are visible within their lexical scope and nested sub-scopes.

==== Variable Declaration

Variables are declared (bound) by several PartiQL clauses:

*FROM Clause*

The `FROM` clause introduces variables that bind to elements from collections:

[source, partiql]
----
FROM orders AS o  -- declares variable 'o'
----

[source, partiql]
----
FROM customers AS c, orders AS o  -- declares 'c' and 'o'
----

*LET Clause*

The `LET` clause introduces variables that bind to computed expressions:

[source, partiql]
----
SELECT ...
FROM orders AS o
LET o.quantity * o.price AS total  -- declares variable 'total'
----

*GROUP BY Clause*

The `GROUP BY` clause with `GROUP AS` introduces a variable that binds to the group:

[source, partiql]
----
SELECT sensor, COUNT(g) AS reading_count
FROM logs AS l
GROUP BY l.sensor AS sensor GROUP AS g  -- declares 'sensor' and 'g'
----

*AT Clause*

The `AT` clause in `FROM` introduces a variable for array indices or positions:

[source, partiql]
----
FROM items AS item AT index  -- declares 'item' and 'index'
----

==== Scope Rules

*Rule 1: Visibility*

A variable is visible from its point of declaration through the end of its containing query, including:

* Subsequent clauses in the same query
* Nested subqueries within those clauses
* Nested expressions

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
SELECT c.name, 
       (SELECT VALUE o.total 
        FROM c.orders AS o       -- can access 'c'
        WHERE o.total > 100) AS large_orders
FROM customers AS c
----

Variable `c` (declared in outer `FROM`) is visible in the nested subquery.
====

*Rule 2: Shadowing*

Inner scopes can declare variables with the same name as outer scopes. The inner declaration *shadows* (hides) the outer one within the inner scope:

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
SELECT x.a
FROM db1 AS x
WHERE x.b IN (SELECT x.c FROM db2 AS x)
----

* Outer `x` binds to elements from `db1`
* Inner `x` binds to elements from `db2`
* Within the subquery, `x.c` refers to inner `x` (from `db2`)
* Outside the subquery, `x.b` refers to outer `x` (from `db1`)
====

*Rule 3: Order of Declaration*

Variables must be declared before use. Clauses are evaluated in this order:

1. `WITH`
2. `FROM`
3. `LET`
4. `WHERE`
5. `GROUP BY`
6. `HAVING`
7. `ORDER BY`
8. `LIMIT` / `OFFSET`
9. `SELECT` / `SELECT VALUE` / `PIVOT`

Variables declared in earlier clauses are available in later clauses.

==== Technical Implementation

Lexical scoping is implemented through binding tuple concatenation:

1. Start with the outer scope's variables: stem:[p]
2. When entering a new scope with new variables: stem:[b]
3. Evaluate expressions in concatenated environment: stem:[p||b]
4. If a name appears in both, stem:[b]'s binding (the inner one) wins

This mechanism naturally implements shadowing: inner variables override outer ones.

[[sec:name-resolution]]
=== Name Resolution

*Name resolution* is the process of determining which declaration a name reference refers to. PartiQL's resolution rules balance SQL compatibility with support for nested data navigation.

==== Unqualified vs. Qualified Names

*Unqualified Name*

A simple identifier: `x`, `customer`, `total`

Resolution depends on context:

* If a variable with this name exists in scope, resolves to the variable
* Otherwise, if a database object with this name exists, resolves to the database object
* Otherwise, compilation error

*Qualified Name*

Multiple identifiers separated by dots: `mydb.users`, `catalog.schema.table`

* Always resolves to database environment (never to variables)
* Chooses the longest matching database object name
* Remaining parts are tuple path navigation

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
FROM company.hr.employees AS e
----

* `company.hr.employees` is a qualified name
* Might resolve to database object `company.hr.employees`
* Or might resolve to `company.hr` with `.employees` as tuple navigation
* The implementation chooses the longest match that exists in stem:[p_0]
====

==== The @ Symbol

The `@` symbol forces a name to resolve as a variable, never as a database object:

* `@x` - explicitly refers to variable `x`
* If no variable `x` exists, falls back to database object `x`
* Useful when database object names might conflict with variables

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

Given database objects `users` and `orders.details`:

[source, partiql]
----
FROM users AS u, @u.orders AS o
----

* `users` resolves to database object (in `FROM`)
* `@u` explicitly refers to variable `u`
* `@u.orders` navigates into variable `u`'s `orders` attribute
====

==== Context-Dependent Resolution

Resolution rules differ between `FROM` clauses and other clauses, ensuring SQL compatibility:

*In FROM Clause*

Database names have priority:

1. Try to resolve as database object (qualified or unqualified)
2. If not found, try to resolve as variable
3. If neither found, compilation error

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
FROM orders AS o, o.items AS i
----

* `orders` - resolves to database object
* `o.items` - `o` is a variable (declared on left), `.items` navigates into it
====

*In Non-FROM Clause*

Variables have priority:

1. Try to resolve as variable
2. If not found, try to resolve as database object
3. If neither found, compilation error

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
*Example:*

[source, partiql]
----
SELECT o.total
FROM orders AS o
----

* `o` - resolves to variable (declared in `FROM`)
* `.total` - navigates into variable `o`
====

==== Resolution Algorithm

For a name or path stem:[i_1.i_2. ... .i_n]:

*Step 1: Check for @ prefix*

If name starts with `@`:

* Strip the `@` and resolve stem:[i_1] as variable
* If variable stem:[i_1] exists, use it; otherwise try longest matching database name
* Remaining parts are tuple path navigation

*Step 2: Determine context*

* Is this a `FROM` clause path?
  ** A path is a `FROM` clause path if it appears directly in a `FROM` clause
  ** Not if it's in a subquery within the `FROM`

*Step 3: Apply context rules*

If `FROM` clause path:

1. Find longest matching qualified name in database environment
2. If found, use it; remaining parts are tuple navigation
3. Otherwise, try to resolve stem:[i_1] as variable

If non-`FROM` clause path:

1. Try to resolve stem:[i_1] as variable
2. If found, remaining parts are tuple navigation from variable
3. Otherwise, find longest matching qualified name in database environment

==== Complete Example

.{nbsp}
[%unbreakable]
[subs="+normal"]
====
Given database objects: `catalog.users`, `config`, `orders`

[source, partiql]
----
SELECT u.name,
       config.timeout,                -- database object
       o.items                        -- variable navigation
FROM catalog.users AS u,              -- database object (qualified)
     config AS c,                     -- database object
     u.order_history AS o             -- variable 'u', path navigation
WHERE o.total > c.threshold           -- both variables
  AND o.date > config.start_date      -- 'config' database object (prioritizes variable, but none exists)
----

Resolution:

* `catalog.users` → database object (qualified name in `FROM`)
* `config` (first) → database object (unqualified name in `FROM`)
* `u.order_history` → variable `u`, path `.order_history`
* `u.name` → variable `u`, path `.name`
* `config.timeout` → database object `config`, path `.timeout`
* `o.items` → variable `o`, path `.items`
* `o.total` → variable `o`, path `.total`
* `c.threshold` → variable `c`, path `.threshold`
* `config.start_date` → database object `config`, path `.start_date`
====

==== Summary

[cols="2,2,2", options="header"]
|===
|Context |Unqualified Name |Qualified Name

|FROM clause
|1. Database object +
2. Variable
|Database object only (longest match)

|Other clauses
|1. Variable +
2. Database object
|Database object only (longest match)

|With @ prefix
|1. Variable +
2. Database object
|Variable (first part), then longest database match
|===

These resolution rules ensure SQL compatibility while enabling PartiQL's extensions for nested data and semi-structured queries.
